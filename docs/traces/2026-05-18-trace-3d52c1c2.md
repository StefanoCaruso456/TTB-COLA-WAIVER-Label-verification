## How we got to 5.7s — and how close we were

The 5 s SLO budget breaks down like this:

```
   5.0 s SLO ─────────────────────────────────────────┤
                                                      │  miss by 0.7 s
   5.7 s observed Gemini call ────────────────────────┼──┤
                                                      │  near-miss, not a blowout
```

Two levers were available before this trace was captured:
1. **Drop `rawText` from the prompt** (shipped in PR #25). Cut completion tokens from ~1544 → 1204. That's the 1 s improvement visible in the table above.
2. **Swap the deployed model from `flash` to `flash-lite`** (also coded in PR #25, with `extraction-service-factory.ts:18` falling back to lite when `GEMINI_MODEL` is unset). **Never landed in production** because Railway's Variables panel still has `GEMINI_MODEL=gemini-2.5-flash` set, and an explicit env var always wins over a code default.

Lever 1 worked. Lever 2 has not been pulled. The two levers were sized to be additive: lever 1 shaved ~1 s, lever 2 is expected to shave another ~1.5 s (the README documents `flash-lite` as "~2× faster decode" than `flash`). With both pulled, the projected Gemini call is ~3 s — comfortably under the 5 s SLO and matching the README's `~3–4 s` claim.

## Why the env var still wins

`lib/services/extraction-service-factory.ts:18`:

```ts
model: env.GEMINI_MODEL ?? "gemini-2.5-flash-lite",
```

The `??` operator returns the right-hand default **only when the left-hand value is `null` or `undefined`**. Railway has `GEMINI_MODEL=gemini-2.5-flash` set, so `env.GEMINI_MODEL` is the string `"gemini-2.5-flash"` — not nullish — and the code default never fires. The trace confirms this directly: `metadata.model = "gemini-2.5-flash"`.

The fix is one click in the Railway Variables panel: **delete the `GEMINI_MODEL` variable** (or change its value to `gemini-2.5-flash-lite`). No code change. No PR. No redeploy needed beyond the variable update.
